| # | 子项 | 配置与步骤 | 测试图案 | 判定标准 | 备注 |
|---|---|---|---|---|---|

| 2.2 | 下降沿采样 | 配 `PCKPOL` 为下降沿采样 | 数据在 PIXCLK 下降沿附近稳定 | DMA buffer 与预期图案一致 | `init.pckpol = false` |

|---|---|---|---|---|---|
| 4.1 | Mode 2 正常帧 | `ESS=`内嵌，`EDM=0`，在 `DCI_ESCR` 配 FS/FE/LS/LE | `FF 00 00 FS`、`FF 00 00 LS`、图像数据、`FF 00 00 LE`、`FF 00 00 FE` | 只存图像数据；同步码字节不入 buffer；帧/行边界正确 | |

| 4.3 | 同步码被排除 | 内嵌模式 + 已知同步码 | 在负载前后插入 `FF 00 00 XY` 序列 | DMA buffer 中不出现任何 `FF 00 00 XY` 同步字节 | |
| 4.4 | FE 通配 | 把 FE 码设为 `0xFF` | 发一个与 FS/LS/LE 都不同的码值 | 未使用的码按 spec 被解释为有效的 FE 码 | |
| 4.5 | 内嵌码 unmask | 配 `DCI_ESUR` 掩码 | `FSC=0xA5`，FS unmask=`0x10`；遍历所有未掩蔽位 | 只比较被掩蔽的位；掩蔽位匹配时 FS 被识别 | |
| 4.6 | 错误前缀 | 用非法同步前缀 | 发 `FE 00 00 XY`、`FF 01 00 XY`、`FF 00 01 XY` | 非法前缀不被识别为同步码，且不得产生帧/行事件 | |

## 7. Crop 功能（6 条）

| # | 子项 | 配置与步骤 | 测试图案 | 判定标准 |
|---|---|---|---|---|
| 7.1 | 全帧 crop | 使能 crop，起点 `(0,0)`，尺寸 = 全帧 | 坐标图案 `Pixel(x,y) = (y*width+x) & 0xFF` | DMA 结果与关闭 crop 的全帧结果完全一致 |
| 7.2 | 居中窗口 crop | 把 crop 起点与尺寸配成居中窗口 | 坐标图案，宽高已知 | 只存选中的矩形窗口；**首字节对应配置的起始坐标** |
| 7.3 | 左上边界 | crop 起点 `(0,0)`，小窗口 | 坐标图案 | 首个采到的数据对应源坐标 `(0,0)`；窗口尺寸正确 |
| 7.4 | 右下边界 | crop 窗口结束于帧右下角 | 坐标图案；窗口末端等于最后一个有效像素/行 | 不多一行/一像素，也不缺预期数据 |
| 7.5 | CAPCNT 非 4 倍数 | 水平 crop 尺寸编程为 5/6/7 个像素时钟 | 已知图案，读回采到的长度 | 低 2 bit 被强制清 0；实际水平采集数按硬件定义 |
| 7.6 | VSYNC 提前结束 | 在达到 crop 行数前就结束帧 | crop 期望的行数多于帧实际提供的 | 采集在 VSYNC/帧结束处停止；若使能则产生 `IT_FRAME` |

> 7.1 是「crop 路径与非 crop 路径等价」的基准用例，最适合作为 crop 组的第一条。
> 7.5 直接对应 **§14 待确认项**：`CAPCNT` 到底是 N-1 编码还是「N 且强制清低 2 bit」。驱动当前按 N-1 + 要求 4 倍数实现（`capcnt = w - 1`，非 4 倍数则向下对齐 + 告警），本条用例的结果决定这个实现要不要改。
> 7.6 就是驱动 `DCI_ERROR_FRAME_SHORT` / `DESYNC` 的触发源（DESIGN.md §7.1 第 2 种失步情形）。

## 8. DMA 与 FIFO（7 条）

| # | 子项 | 配置与步骤 | 测试图案 | 判定标准 |
|---|---|---|---|---|
| 8.1 | 每 32-bit word 一次 DMA 请求 | 使能 DMA，观察请求次数 | 8-bit 模式：4 字节；10-bit 模式：2 个样本 | 每凑满一个 32-bit word 触发一次 DMA 请求 |
| 8.2 | 精确传输长度 | 采集已知帧尺寸 | 固定宽高 + 已知每像素字节数 | DMA 的 word/字节计数等于按对齐算出的预期帧大小 |
| 8.3 | DMA 目的地址递增 | 采集多个 word 到 RAM | 递增图案，使能 DMA 内存地址递增 | RAM 地址正确递增，数据顺序保持 |
| 8.4 | FIFO 正常负载 | 让 DMA 带宽高于 DCI 输入速率 | 在合法时钟比内发长有效流 | 无溢出；数据内容正确 |
| 8.5 | 深度内的 FIFO 背压 | 暂停 DMA，但不超过 8 个 FIFO word | 短暂阻塞 DMA，在 FIFO 满之前恢复 | 无数据丢失，无 `OVR` 中断 |
| 8.6 | FIFO 溢出 | 暂停 DMA 足够久，超过 8-word FIFO 深度 | DMA 无法读取时发超过 8 个 32-bit word | 产生 `OVR` 中断；FIFO 被复位；当前帧被丢弃 |
| 8.7 | 溢出后恢复 | 溢出后继续发下一帧 | `OVR` 帧之后，发新的帧起始与图像 | DCI 等待新帧起始，下一帧可正常采集 |

> 8.1 是 `SRC_MSIZE = Msize_1` 的依据（DESIGN.md §5：配大 burst 会欠载）。
> 8.2 是描述符 `Σ CTL_HIGH == frame_words` 的硬件侧确认。
> 8.7 是驱动 `resync` 的可行性前提 —— spec §2.8 的「DCI 自愈」在硬件上确实成立，驱动才只需重同步 DMA 侧。
> **8.5/8.6 的制造手段**见 §15.5（不能靠"想办法让 DMA 慢"，要可控地停）。

## 9. JPEG 模式（6 条）

| # | 子项 | 配置与步骤 | 测试图案 | 判定标准 | 备注 |
|---|---|---|---|---|---|
| 9.1 | 4 字节对齐的 JPEG 流 | `JPEG=1`，硬件同步 | 在 HSYNC 数据使能下发长度为 4N 的类 JPEG 字节流 | DMA 数据与输入流完全一致 | |
| 9.2 | JPEG 长度 4N+1 | `JPEG=1`；发非对齐流 | 发 5 字节后结束帧 | 最后一个 32-bit word 的剩余 **3 字节补 0** | |
| 9.3 | JPEG 长度 4N+2 | `JPEG=1`；发非对齐流 | 发 6 字节后结束帧 | 最后一个 word 的剩余 **2 字节补 0** | |
| 9.4 | JPEG 长度 4N+3 | `JPEG=1`；发非对齐流 | 发 7 字节后结束帧 | 最后一个 word 的剩余 **1 字节补 0** | |
| 9.5 | JPEG 变长消隐 | `JPEG=1`；改变包间消隐 | 各包之间用长度不等的 HSYNC 非有效期分隔 | 只存 HSYNC 数据使能期的数据；包间消隐被忽略 | |
| 9.6 | JPEG 不支持的组合 | 试 JPEG + crop、JPEG + 内嵌同步 | 分别配 JPEG+crop 和 JPEG+内嵌 | **固件拒绝**该组合，或硬件行为符合 RTL 定义 | spec 说 JPEG 不支持 crop 与内嵌同步 |

> 9.2 ~ 9.4 决定驱动的上报长度：**驱动如实上报 DMA 实际搬运量，不裁掉补的 0**（DESIGN.md §9.3）。这三条用例要顺带记录「上报长度 − 真实 JPEG 长度」是否恰好等于补零字节数。
> 9.6 在驱动侧是确定性的：`DCI_Capture_Init()` 返回 `DCI_ERROR_MODE_CONFLICT`，属**固件拒绝**分支，不需要触硬件。

| 11.6 | 四取二 | 配四取二选择 | 同上 | 每 4 字节组采配置的那 2 个字节 | `bsm = 2_OF_4` |
| 11.7 | 垂直 + 水平同时缩减 | 同时使能垂直与水平缩减 | 坐标图案，行位置与字节位置均唯一 | 输出尺寸与内容符合组合缩减规则 | `lsm && bsm != ALL` |

> **这 7 条直接验证驱动 `frame_bytes` 公式的每一项**（DESIGN.md §6.2）：11.2 验 `lines_out` 的 `oels` 分支，11.4 ~ 11.6 验 `bsm_num/bsm_den`，11.7 验两者相乘。
> 11.5 的备注「仅 8-bit」= 驱动的 `bsm != ALL && edm != 0 → MODE_CONFLICT` 校验（寄存器表：*valid only when EDM[1:0]=00*）。
> 11.7 建议用坐标图案 `(y*W+x) & 0xFF` —— 缩减后每个字节的来源坐标都能反算，比等值图案强得多。

## 12. 中断（7 条）

**每条子用例都要跑完这 6 项检查**（原表在「测试图案」列统一列出）：

```
中断清除 (ICR)      中断状态 (RIS)      中断使能 (IER)
中断屏蔽 (MIS)      中断触发条件        中断可重复触发
```

| # | 子项 | 配置与步骤 | 触发方式 | 判定标准 | 备注 |
|---|---|---|---|---|---|
| 12.1 | LINE 中断 | 使能 LINE 中断，发一行或多行 | 在硬件同步或内嵌同步模式下完成一个有效行 | `RIS.LINE=1`；若 `IER.LINE=1` 则 `MIS.LINE=1` 且全局 IRQ 有效 | 驱动默认**不开** LINE（466 行 @60fps = 28k 次/秒），须注册 `line_event` 回调才开 |
| 12.2 | FRAME 中断 | 使能 FRAME 中断，发一个完整帧 | 完成一个快照帧或连续帧 | `RIS.FRAME=1`；若使能则 `MIS.FRAME=1` 且 `IT_DCI` 有效 | 驱动**恒开**，是帧边界的唯一权威 |
| 12.3 | VSYNC 中断 | 硬件同步模式下使能 VSYNC 中断 | 翻转 VSYNC 指示帧同步事件 | `RIS.VSYNC=1`；屏蔽后的状态跟随 `IER` 设置 | 须注册 `vsync_event` 才开 |
| 12.4 | OVR 中断 | 强制 FIFO 溢出 | 阻塞 DMA 直到 FIFO 溢出 | `RIS.OVR=1`；若使能则 `MIS.OVR=1` 且全局 IRQ 有效 | 驱动**恒开**（自身 resync 需要） |
| 12.5 | ERR 中断 | 用内嵌同步的非法序列 | 发错误的内嵌码序 | `RIS.ERR=1`；若使能则 `MIS.ERR=1` 且全局 IRQ 有效 | **仅内嵌模式**；驱动恒开 |
| 12.6 | 中断屏蔽/解屏蔽 | 在中断事件前后翻转 `IER` 位 | `IER` 位=0 时触发事件；再用 `IER` 位=1 重复 | 屏蔽时：`RIS=1`、`MIS=0`、无全局 IRQ；解屏蔽时：`RIS=1`、`MIS=1`、全局 IRQ 有效 | **驱动最关键的一条**，见下 |
| 12.7 | 多中断逻辑或 | 同时触发两个中断源 | 例：帧尾与行尾同时发生 | 任一 `MIS` 位为 1 则全局 `IT_DCI` 有效；所有 pending 的 `RIS`/`MIS` 位都可读 | 驱动 `DCI_Handler()` 一次处理多位 |

> **12.6 必须严格执行。** 驱动有两处直接依赖「`RIS` 与 `IER` 无关地 latch」这条性质：
> 1. `IT_FRAME` 恒开的论证（DESIGN.md §7.2）；
> 2. 用 latch 的 `RIS.FRAME` 解 `GDMA_INT_Transfer` 与 `IT_FRAME` 的竞态（`dci_dma_isr()`），**这是驱动里唯一一处不用超时就能定论的地方**。若 12.6 实测发现 `RIS` 在屏蔽期不置位，`dci_dma_isr()` 的判据要整个重做。
>
> 另需补测一条原表没有的：**`RIS` 是单 bit 而非计数器** —— 屏蔽期间连来 2 次 `FRAME`，解屏蔽后只触发 1 次。这条是「连续模式不能屏蔽 `FRAME`」的依据（DESIGN.md §7.2）。

| # | 子项 | 配置与步骤 | 测试图案 | 判定标准 | 备注 |
|---|---|---|---|---|---|
| 13.1 | 典型帧尺寸 | 跑常见分辨率 | 320×240、640×480，用递增或 CRC 图案 | 数据、帧计数、行计数、DMA 计数、中断都正确 | 均为 1 块（DESIGN.md §6.3） |

## 15. 测试工程思路

### 15.1 分层：哪些必须硬件做，哪些驱动层就能做

73 条用例按「需要什么能力」分四层，工程量差别巨大：

| 层 | 需要的能力 | 用例 | 条数 |
|---|---|---|---|
| **A. 纯软件（不需要任何激励）** | 只调驱动 API，检查返回码与内部状态 | `DCI_RegTest()` 寄存器自检（连 sensor 都不用接，见 S25）；9.6、13.3 的固件拒绝分支；全部参数校验 | ~9 |
| **B. 常规激励（真 sensor 或固定图案发生器就够）** | 能产出合法的帧流 | 1.x、3.1、3.5、5.x、6.x、7.1~7.4、8.1~8.4、9.1、10.x、11.x、12.1~12.3、13.1、13.2、13.4、13.5 | ~45 |
| **C. 可编程激励（必须能构造非法/边界时序）** | 逐字节控制数据、消隐期插值、改极性、改时钟比、造非法码序 | 2.x、3.2~3.4、4.x、7.5、7.6、9.2~9.5 | ~17 |
| **D. 需要干扰 DMA** | 可控地阻塞 GDMA 通道 | 8.5、8.6、8.7、12.4 | 4 |

结论：**C 层决定工程选型** —— 只要有 17 条用例需要构造非法时序，真 sensor 就不够用，必须有可编程激励源。

### 15.2 激励源选型

| 方案 | 能覆盖 | 缺点 | 建议 |
|---|---|---|---|
| **真 camera sensor** | A + B | 完全无法造非法时序（C）；消隐期插值做不到；PIXCLK 频率只有几档 | 作为**集成验收**手段，不作为用例执行主力 |
| **FPGA 上的 DCI 图案发生器 RTL** | A + B + C + D | 需要写一个 stimulus 模块 | **推荐主力**。DCI 是纯从设备、只有 4 组输入信号（D[9:0]/HSYNC/VSYNC/PIXCLK），激励模块很小 |
| **另一颗 MCU 用 GPIO/SPI 模拟** | A + B，部分 C | PIXCLK 打不快，2.4/2.5 那档时钟比测不了；时序抖动大 | 只适合早期打通 |

**推荐做法**：FPGA 上放一个由寄存器配置的 stimulus 模块，参数化以下几项，则 C 层 17 条用例全部可脚本化：

```
分辨率 W × H                      消隐长度 hblank / vblank（可逐帧变，覆盖 3.5）
数据位宽 8/10                     极性 pckpol / hspol / vspol（覆盖 2.1~2.3、3.1）
PIXCLK 分频比                     消隐期填充值（覆盖 3.2 的 0xEE / 3.3 的 0xDD）
图案类型（见 §15.4）              内嵌码序（可注入非法序列，覆盖 4.x）
帧数与逐帧图案 ID                 流长度（可设 4N+1/2/3，覆盖 9.2~9.4）
```

### 15.4 图案设计与校验手段

用例的判定质量几乎完全由图案决定。四种图案，按能力递增：

| 图案 | 定义 | 能查出 | 用于 |
|---|---|---|---|
| **等值** | 整帧同一个值 | 只能查「有没有数据」 | 3.2/3.3 的消隐期插值（`0xEE`/`0xDD` 只需"不出现"） |
| **递增** | `byte[i] = i & 0xFF` | 丢字节、重复字节 | 1.x、11.x |
| **坐标** | `Pixel(x,y) = (y*W + x) & 0xFF` | **每个字节都能反算来源坐标** → 错位、偏移、缩减相位一次看清 | 7.x crop、11.7 组合缩减 —— 原表已指定 |
| **帧 ID + CRC** | 每帧首字节放帧号，整帧算 CRC | 大数据量下省内存（不用存整帧） | 13.2 最大尺寸、13.4 长压力 |

三条贯穿所有用例的常驻检查：

1. **Buffer 哨兵（13.5）** —— buffer 前后各放几个 `0xA5A5A5A5`，**每条用例结束都查**，不要只当一条独立用例。这是唯一能廉价抓到「描述符 `DAR`/`BLOCK_TS` 算错」的手段，而分块算错的第一表现就是越界写。
2. **`DCI_GetStats()` 全量比对** —— 每条用例结束后断言 `frames_done`/`frames_dropped`/`ovr_count`/`err_count`/`resync_count`/`suspend_count`/`buf_overflow` 全部等于预期值（多数用例应当是「除 `frames_done` 外全为 0」）。比只看数据内容更容易定位。
3. **失败时自动 `DCI_RegDump()`** —— 用例失败的那一刻寄存器状态才有诊断价值。`DCI_RegSnapshot()` 是 ISR 安全的，可以在 ISR 里抓、回到线程再打印（DESIGN.md §13.1）。

**分块路径的覆盖问题**：只有 13.2（2048×2048）会走到 `chunks_per_frame = 2/3`。若 FPGA 内存装不下，把 `DCI_MAX_BLOCK_TS` 临时编译成一个很小的值（例如 `4096`），常见分辨率就会被强制分块，从而用 640×480 覆盖多块组帧逻辑。这比"内存不够所以不测分块"好得多 —— 分块是驱动里最容易错的部分。

### 15.5 8.5 / 8.6 / 12.4 怎么可控地制造 FIFO 溢出

「暂停 DMA」不能靠"想办法让 DMA 慢"，那样不可复现。三种可控手段，按推荐度：

| 手段 | 做法 | 精度 |
|---|---|---|
| **挂起 GDMA 通道** | `GDMA_SuspendCmd(chan, ENABLE)` → 等 N 个 PIXCLK → `DISABLE` | **最好**。停多久完全可控，`N < 8 word` 覆盖 8.5，`N > 8 word` 覆盖 8.6 |
| 压满 AHB | 让别的 master（另一条 GDMA 通道跑大块 memcpy）抢总线 | 只能定性，不能精确控制"少于 8 个 word" |
| 把 DMA 配到慢速目标 | 目的地址指向低速外部存储 | 不可控，且改变了被测配置 |

选第一种，并且注意：**8.5 与 8.6 的区别只有暂停时长**，所以这两条应当写成同一个参数化用例，扫 `N = 1..16` word，观察 `OVR` 恰好在超过 FIFO 深度时出现 —— 顺带把 §17 待验证项 #7「FIFO 实际深度」测出来（spec 只标了「8-word？」带问号）。

### 15.6 执行顺序建议

用例之间有依赖，乱序执行会出现「前一条的失败伪装成后一条的 bug」。建议按此顺序：

```
1. 主机侧全部用例                       ← 无硬件依赖，先全绿
2. §14 的 8 项待确认（尤其第 5 项 CAPCNT）  ← 定判据，否则 crop 6 条无法判
3. 1.x 数据打包 → 3.x 硬件同步           ← 最基础，错了后面全错
4. 12.x 中断（尤其 12.6 的 RIS latch）    ← 驱动竞态判据的前提
5. 5.x 采集模式 → 8.1~8.4 DMA 正常路径
6. 7.x crop → 11.x 分辨率修改            ← 依赖 frame_bytes 公式已被 1.x/3.x 证实
7. 6.x FCRC → 9.x JPEG → 10.x 格式
8. 8.5~8.7 溢出 → 2.4/2.5 时钟边界        ← 破坏性/表征类，放后面
9. 13.x 边界与压力                       ← 最后跑，最耗时
```

| S16 | `Reconfig` 先校验后破坏 | 参数非法时返回错误码，**正在跑的采集完全不受影响** | §12.3 |
| S17 | `Reconfig` 持锁拒绝 | 有 buffer 被持有 → 返回 `BUSY` 且不动硬件 | §12.3 |
| S18 | 纯软件字段快路径 | 只改 `on_busy`/`notify_mode`/回调指针 → 不停采集、不重装 DMA | §12.3 |
| S19 | `Abort()` 契约 | 强行回收 `buf_lock_mask`；返回后此前交付的帧立即失效；之后调 `ReleaseBuffer()` 是无害空操作 | §11.5 |
| S20 | capture mode 锁定 | 首次 `Start()` 定拓扑，后续传不同 mode → `INVALID_PARAM` | §12.2 |
| S21 | `SetBuffers()` 快路径 | 只改描述符 `DAR`，`ENABLE` 保持 1；持锁时返回 `BUSY` | §12.4 |
| S22 | 分块组帧正确性 | 2 块/3 块时 `Σ CTL_HIGH == frame_words`，末块允许更短，帧数据连续无缝 | §6.3（配合 13.2 或 §15.4 的缩小 `BLOCK_TS` 手段） |
| S23 | 行长非 4 倍数的退化 | 如 466 宽单色 → 退化为 word 对齐分块，`line_aligned = 0` 且数据正确 | §6.2 |
| S24 | 中断使能策略 | 未注册 `line_event` 时 `IER.LINE` 必须为 0（对照 ST 的无条件使能） | §11.4 |
| S25 | **寄存器读写自检**（`DCI_RegTest()`） | 位可写性 / 保留位为 0 / 地址不混叠 / `ICR` write-1-only / `MIS = RIS & IER`；时钟未开或基址错时报 `NO_RESPONSE`；结束后所有寄存器回到复位值、`DR` 一次未读、状态机回 `RESET` | §13.6 |

> S1 ~ S25 中已有 20 余条在主机侧跑通（DESIGN.md §18「主机侧验证」列出了覆盖范围），S8/S9/S13/S14 的**硬件侧触发**仍依赖 7.6 与 9.2~9.4。
>
> **S25 是唯一一条既属驱动层、又能在真机上独立跑的**：它不需要 sensor、不需要 DMA、不需要激励源，因此是 bring-up 的第一道工序（TESTAPP.md §9 的 L0）。它顺带定论 §14 的第 5 项（`CAPCNT` 编码），把那个开放问题从「等 7.5 用例」提前到「上电第一秒」。
>
> **S12 值得单独说明**：它是实现阶段才发现的设计漏洞（resync 无条件重启到 group 0，会覆写消费者手上的 buf0），原设计文档和原测试表都没有。这类「跨机制交互」的缺陷正是 IP 验证表结构上覆盖不到的 —— 原表按寄存器功能分项，而漏洞出在两个功能的交界处。
